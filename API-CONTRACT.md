# Win Computer UI/API contract

Use a typed Express/tRPC backend and the starter's `trpc` React client, using nested routers as below. Auth status and setup/login are public; all other procedures require a valid session and normal procedures are rejected while a password change is required. Admin = owner or admin. Business capability approvals must actually authorize the requested non-default action. Server must return only safe fields, no hashes/secrets.

- `auth.status.query()` -> `{ initialized: boolean, approvalConfigured: boolean, user: null | { id:number, username:string, name:string, role:'owner'|'admin'|'staff', mustChangePassword:boolean } }`.
- `auth.setup.mutate({username,password,approvalPassword})`, `auth.login.mutate({username,password})`, `auth.changePassword.mutate({currentPassword,newPassword})`, `auth.logout.mutate()` -> `{success:true}`. Setup only once and only with configured approval credential. Login/logout update session cookie.
- `overview.stats.query()` -> `{ receiptsCount:number, income:number, refunds:number, openingCash:number|null, cashBalance:number|null, byMethod:{cash:number,kbzpay:number,wavepay:number}, recentReceipts: Receipt[] }`. Amounts are integer MMK. Cash balance = known opening + net recorded cash received, otherwise null; don't claim profit.
- `receipts.list.query()` -> `Receipt[]`; `receipts.create.mutate({type:'sale'|'service',description:string,amount:number,method:'cash'|'kbzpay'|'wavepay',paymentReceived:boolean,customer?:string})` -> `Receipt`; `receipts.transition.mutate({id:number,action:'void'|'refund',reason:string,approvalPassword:string})` -> `Receipt`. `Receipt` safe fields are `{id:number,number:string,type:'sale'|'service',description:string,amount:number,method:'cash'|'kbzpay'|'wavepay',paymentReceived:boolean,status:'active'|'void'|'refunded',customer:string|null,createdAt:Date|string,createdByName:string}`. A received active receipt cannot be voided as if it never received funds; refund records a compensating amount, state transitions are guarded and audited. A pending receipt may be voided but cannot be refunded.
- `prices.list.query()` -> `{id:number,key:string,nameEn:string,nameMm:string,amount:number|null,updatedAt:Date|string|null}[]`. Four fixed service categories may exist but no invented amounts. `prices.update.mutate({id:number,amount:number|null})` -> `{success:true}`; admin or user with approved `manage_prices` capability. Audit old/new.
- `team.list.query()` -> `{id:number,username:string,name:string,role:'owner'|'admin'|'staff',mustChangePassword:boolean,active:boolean}[]`. Admin only. `team.create.mutate({username,name,password,role:'staff'|'admin'})`, `team.reset.mutate({id:number,password})` -> `{success:true}`; resets force password change and revoke sessions.
- `permissions.list.query()` -> `{id:number,requesterId:number,requesterName:string,capability:'manage_prices',reason:string,status:'pending'|'approved'|'rejected',createdAt:Date|string,decisionNote:string|null}[]` for own requests or all for admins. `permissions.request.mutate({capability:'manage_prices',reason:string})`; `permissions.decide.mutate({id:number,decision:'approved'|'rejected',note:string})` -> `{success:true}`; approved capability is checked in prices.update.
- `notices.list.query()` -> `{id:number,titleEn:string,titleMm:string,bodyEn:string,bodyMm:string,audience:'all'|'owner'|'admin'|'staff',type:'announcement'|'maintenance'|'notification',read:boolean,createdAt:Date|string}[]` filtered by audience. `notices.create.mutate({titleEn,titleMm,bodyEn,bodyMm,audience:'all'|'owner'|'admin'|'staff',type:'announcement'|'maintenance'})` and `notices.markRead.mutate({id:number})` -> `{success:true}`. Permission request/decision generates appropriate in-app notices.
- `admin.serverStatus.query()` -> `{status:'open'|'closed',messageEn:string,messageMm:string,startAt:string|null,endAt:string|null,scheduleIsConfigured:boolean,note:string}`. `admin.setServerStatus.mutate({status:'open'|'closed',messageEn:string,messageMm:string,startAt:string|null,endAt:string|null})` -> `{success:true}`. This is the business system availability/maintenance state, not an OS or remote power control. Owner/admin only may change it; login, notices, password change, and admin actions remain available while closed. Staff business writes are server-side blocked while closed. Every transition is audited with old/new status, actor, message, and schedule. A real open/closed transition creates one targeted in-app notification per active user (including admins/owners), with Burmese/English title/body and actor/time/schedule; saving without a status transition does not create a duplicate transition notice. `admin.maintenance.query()` and `admin.setMaintenance.mutate({enabled:boolean,messageEn:string,messageMm:string,startAt:string|null,endAt:string|null})` remain compatibility aliases over the same state and notification behavior. Schedule fields are informational only; no background scheduler is claimed. `admin.setOpeningCash.mutate({amount:number})` -> `{success:true}`; no amount prefilled.
- `audit.list.query()` -> `{id:number,actorName:string,action:string,entityType:string,entityId:string,details:string,createdAt:Date|string}[]`, admin only.

Print is a browser compact print view with a bilingual receipt and user's logo. PDF saving can use the browser's Save as PDF print destination; do not claim an independently generated PDF. Run user-facing error handling from actual backend messages.

## Next-phase backend additions

- `roles.list.query()`, `roles.create.mutate({name,description?,capabilities})`, `roles.update.mutate({id,name,description,active,capabilities})`, `roles.delete.mutate({id})`, `roles.assign.mutate({userId,roleId:number|null})`, and `roles.grantUser/revokeUser.mutate({userId,capability})` manage custom roles. Owners/admins may manage roles; capability checks are enforced server-side. Built-in owner/admin bypass capability checks.
- `catalog.products.list/create/update`, `catalog.categories.list/create`, and `catalog.services.list/create/update` expose active product/SKU/unit/purchase-sale price, categories, and service types/prices. Catalog writes require `manage_catalog` (owner/admin or a granted custom/direct capability).
- `receipts.create` accepts optional `items[]` with exactly one `productId` or `serviceTypeId`, description, quantity, and unitPrice; item totals must equal the receipt amount. `wc_receipt_items` preserves the current receipt shape.
- `settings.get.query()` and owner/admin-only `settings.update.mutate({welcomeTextMm,contactViber,contactTelegram,contactPhone,logoReference})` manage configurable Burmese welcome and business contacts/logo reference.
- `lifecycle.deactivate/restore/delete.mutate({id})` provide audited safe account lifecycle actions; delete is a soft delete, owner/self deletion is blocked, and deactivation revokes sessions. Existing `team.update` edits staff/admin name and built-in role; `team.reset` forces password change and revokes sessions; role assignment is available through `roles.assign`.
- `exports.csv.query({table:'receipts'|'products'|'services'|'users'|'audit'})` returns `{filename,mime,content}`. `content` is UTF-8 BOM CSV and opens directly in Excel; users/audit require `manage_users`/`view_audit` capability respectively.
- `notices.create` additionally accepts optional `targetUserId`; existing audience values target roles, and `notices.markRead` is the acknowledge operation. All admin mutations continue to write `wc_audit`.

## Employee profiles and authority policy

- `profile.get.query()` returns the signed-in employee's additive profile fields (`phone`, `businessEmail`, `address`, optional `dateOfBirth`, `nationalId`, `emergencyContact`, `jobTitle`, `avatarReference`, `profileCompleted`). `profile.update.mutate(...)` is protected, records `profile.update` audit entries, and never accepts passwords or secrets. National ID is sensitive and is not exposed through public/auth summary fields.
- Staff accounts with an incomplete profile are shown the completion form before workspace access. Owner accounts may continue to the workspace while the completion request remains documented in-app.
- Custom role create/update/delete, capability grants/revokes, and custom-role assignment are owner-only server procedures. Admins may view the role matrix and manage non-authority lifecycle actions only. Owner accounts cannot be edited, deactivated, deleted, or reassigned; self-destructive lifecycle actions are blocked.
- Employee create, profile-completion request, role changes, deactivation, restoration, and soft deletion create targeted Burmese/English in-app notices for the affected account and relevant administrators/owner. Historical records retain the original user attribution.
